BUG 1 — CUSTOMER CHAT LOADING STUCK
==================================================

File:
artifacts/postlap-ai/src/components/HamzawiChat.tsx

Current problem:
"جاري التحميل" is displayed when:
messages.length === 0 && !loading

The `loading` flag only represents active send requests.
It does not represent the initial history-loading lifecycle.

If loadHistory() or the initial API/memory fetch fails, stalls, or never resolves,
messages can remain empty while loading remains false.

Required behavior:

- Customer Chat must always resolve into a usable state.
- "جاري التحميل" must NEVER remain indefinitely.
- Add a reasonable timeout/error fallback (approximately 8 seconds is acceptable).
- On history failure/timeout, show the normal welcome message or another existing safe empty-state.
- Do not create a new complicated loading architecture.
- Preserve the existing successful history-loading behavior.
- Make sure initialization failures are handled rather than leaving the UI permanently stuck.

Inspect both:
- loadHistory()
- initialization effect / initial `/api/hamzawi/chat` flow

Do not merely hide the loading text.
Fix the underlying state transition so the component becomes usable.

BUG 3 — GENERATION MARKER MUST BE SERVER-GATED
==================================================

File:
artifacts/api-server/src/routes/hamzawi.ts

Current problem:

The model can emit:
%%GENERATE_POST%%

The route currently processes that marker without sufficiently enforcing the
classified intent.

The classifier can correctly identify:
"شو بتقترح؟"
"شو بتنصحني؟"

as:
general_chat

But if the model violates the prompt and emits the generation marker anyway,
the backend still starts generation.

This MUST be fixed server-side.

Required rule:

Only process %%GENERATE_POST%% when:

intentDecision.intent === 'generate_image'

If the marker appears while intent is anything else:

- DO NOT generate an image.
- Strip the marker from the user-visible response.
- Return the normal text response.

This is a backend safety/consistency guard.

Do not rely only on prompt instructions.

After implementation, manually test at least:

A)
User:
"شو بتقترح؟"

Expected:
Text recommendation.
NO image generation.

B)
User:
"شو بتنصحني؟"

Expected:
Text recommendation.
NO image generation.

C)
An actual explicit image-generation request.

Expected:
Existing generation flow still works.

BUG 4 — PREVIOUS GENERATED IMAGE MUST BE AVAILABLE
==================================================

Files to inspect:

artifacts/api-server/src/routes/hamzawi.ts
artifacts/api-server/src/services/ai/contextBuilder.ts
artifacts/api-server/src/services/media/assetReader.ts

Current behavior:

Uploaded user images are already reconstructed by buildHistoryForAI()
from stored /uploads/ URLs and converted to multimodal/base64 inputs.

Previously generated images are different.

Generated images are currently represented only by textual completion/history information,
so when the user says:

"عدل التصميم السابق"

the model does not actually receive the previous generated image.

Required fix:

When a generated image is persisted in the assistant conversation message,
persist a reference marker containing the generated image's stored /uploads/ URL,
using the existing marker pattern if appropriate.

For example, conceptually:

%%ATTACHED_IMAGE%%{url:'/uploads/...'}

IMPORTANT:
Do NOT blindly copy this exact syntax if the existing parser expects another format.
First inspect the existing attached-image implementation and reuse its established format.

Then ensure buildHistoryForAI():

- detects generated-image attachment markers
- resolves the stored URL to the actual image/base64 representation
- includes it as a multimodal image input for the next AI turn
- respects the existing 6-image cap
- does not break existing user-uploaded image handling

The final behavior must be:

Turn 1:
User requests design → image generated → image stored.

Turn 2:
User says:
"عدل التصميم السابق"

AI receives the actual previous image,
not merely a textual description.

Do NOT introduce a new asset architecture.
Use the existing /uploads/ and attachment/history mechanisms.
